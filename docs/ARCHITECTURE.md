# معماری فنی و محصول — Goli Gift

- وضعیت سند: نسخه 1.0 — مبنای شروع پیاده‌سازی
- تاریخ: 2026-11-20
- مخزن: `Suushian/Goli-Gift`
- زبان محصول: فارسی (RTL)
- سبک بصری: Cute Pixel Art / 8-bit
- دامنه این سند: معماری کل تجربه پنج‌صفحه‌ای؛ پیاده‌سازی UI در فازهای مستقل انجام می‌شود.

---

## 1. چشم‌انداز و هدف

Goli Gift یک تجربه‌ی تعاملی شخصی برای تولد است که مانند یک بازی کوتاه و روایت‌محور طراحی می‌شود. کاربر از یک ورودی رمزگونه عبور می‌کند، خاطرات را می‌بیند، به بازی دعوت می‌شود، به پرسش‌ها پاسخ می‌دهد و در پایان پیام تبریک، هدیه و پیام صوتی را دریافت می‌کند.

اصل اجرایی پروژه: **هر فاز فقط یک صفحه را طراحی، پیاده‌سازی و بازبینی می‌کند.** تا وقتی صفحه‌ی جاری تأیید نشده، فاز بعدی شروع نمی‌شود. با این حال، قراردادهای مشترک و ساختار کل محصول از ابتدا تعریف می‌شوند تا صفحات از هم گسسته نشوند.

## 2. تصمیم‌های محصول و دامنه

### نیازمندی‌های قطعی

1. پنج صفحه با ترتیب روایی مشخص:
   - صفحه ورود رمز تولد
   - صفحه خاطرات
   - صفحه دعوت به بازی
   - صفحه بازی پرسش و پاسخ
   - صفحه پایانی شامل تبریک، افشای هدیه و پخش ویس
2. رابط فارسی و راست‌چین (RTL).
3. سبک Cute Pixel Art با پالت روشن.
4. حضور کاراکتر پیکسلی اختصاصی دوست‌دختر در نقاط منتخب.
5. طراحی و تأیید مرحله‌ای؛ یک صفحه در هر فاز.
6. فناوری توسط تیم فنی انتخاب شود.

### خارج از دامنه نسخه اول

- حساب کاربری، ثبت‌نام یا سیستم چندکاربره
- بک‌اند، دیتابیس و پنل مدیریت
- پرداخت یا فروشگاه
- احراز هویت واقعی و محافظت امنیتی از محتوا
- CMS یا ویرایش محتوای آنلاین
- تحلیل‌گر رفتاری و ردیابی کاربران

## 3. پشته فناوری

| بخش | انتخاب | دلیل |
|---|---|---|
| Runtime | مرورگر مدرن | محصول یک تجربه‌ی مستقل سمت کاربر است |
| Build tool | Vite | توسعه سریع و خروجی استاتیک |
| UI | React | ترکیب‌پذیری و مدیریت state صفحات |
| Language | TypeScript | قراردادهای روشن برای داده و کامپوننت‌ها |
| Routing | React Router | مسیر مستقل برای هر مرحله و پشتیبانی از refresh/deep link |
| Styling | CSS سفارشی و CSS variables | کنترل دقیق پیکسل‌آرت؛ بدون وابستگی غیرضروری به utility framework |
| Tests | Vitest + Testing Library | تست منطق و تعامل کامپوننت‌ها |
| E2E | Playwright (در صورت نیاز CI) | آزمون جریان کامل پنج‌مرحله‌ای |
| Hosting | GitHub Pages یا میزبان استاتیک سازگار | خروجی قابل انتشار بدون سرور |

**تصمیم:** در نسخه اول Tailwind اضافه نمی‌شود؛ جزئیات pixel border، الگوهای tiled و کنترل دقیق مقیاس پیکسل با CSS اختصاصی ساده‌تر و قابل پیش‌بینی‌تر است. کتابخانه‌ی انیمیشن نیز تا زمانی که CSS transitions/keyframes کافی باشند اضافه نمی‌شود.

نسخه دقیق پکیج‌ها هنگام ایجاد scaffold با نسخه‌های پایدار سازگار انتخاب و در lockfile تثبیت می‌شود.

## 4. معماری سطح بالا

معماری از نوع **Static Single-Page Application** است:

```
Browser
  └── React Application
      ├── App Shell (RTL, theme, global layout)
      ├── Router
      │   ├── /              EntryPage
      │   ├── /memories      MemoriesPage
      │   ├── /invitation    InvitationPage
      │   ├── /game          QuizPage
      │   └── /final         FinalePage
      ├── Shared UI
      │   ├── PixelPanel / PixelButton
      │   ├── PixelCharacter
      │   ├── Dialog / Progress / AudioPlayer
      │   └── PageTransition
      ├── Domain
      │   ├── journey state
      │   ├── quiz validation
      │   └── content models
      └── Static Assets
          ├── sprites
          ├── photos
          ├── audio
          └── fonts
```

صفحات، داده‌ی محتوایی و اجزای نمایشی را مصرف می‌کنند؛ منطق پیشرفت داستان و اعتبارسنجی پاسخ‌ها در لایه‌ی domain نگهداری می‌شود، نه داخل JSX هر صفحه.

## 5. نقشه صفحات و جریان کاربر

| ترتیب | مسیر | صفحه | هدف و معیار خروج |
|---|---|---|---|
| 1 | `/` | ورود | ورود سال/رمز تولد؛ پاسخ صحیح مسیر خاطرات را باز کند |
| 2 | `/memories` | خاطرات | نمایش روایت، تصاویر، موسیقی و اطلاعات سال تولد؛ CTA ادامه |
| 3 | `/invitation` | دعوت | دعوت روشن برای شروع بازی؛ CTA شروع |
| 4 | `/game` | بازی | نمایش پرسش‌ها، دریافت پاسخ، بازخورد و پیشرفت؛ تکمیل همه پرسش‌ها |
| 5 | `/final` | پایان | تبریک، افشای هدیه و کنترل پخش ویس |

قواعد جریان:
- ترتیب روایت خطی است؛ دسترسی مستقیم به مسیرهای قفل‌شده به اولین مرحله‌ی مجاز هدایت می‌شود.
- refresh نباید پیشرفت معتبر را از بین ببرد.
- کاربر باید بتواند به صفحه قبلی بازگردد، بدون آنکه پاسخ‌های ثبت‌شده پاک شوند.
- شروع مجدد (Replay) از صفحه پایانی، state داستان را به حالت اولیه برمی‌گرداند.
- انتقال بین صفحات کوتاه و قابل کاهش با تنظیمات `prefers-reduced-motion` است.

## 6. معماری State و مدل داده

### Journey State

نمونه قرارداد مفهومی:

```ts
type JourneyStage =
  | "entry"
  | "memories"
  | "invitation"
  | "game"
  | "final";

interface JourneyState {
  unlockedStage: JourneyStage;
  birthdayUnlocked: boolean;
  completedQuestionIds: string[];
  answers: Record<string, string>;
  completed: boolean;
}
```

- State در یک context کوچک یا store سبک داخلی React نگهداری می‌شود؛ در نسخه اول Redux/Zustand لازم نیست.
- persistence با یک کلید نسخه‌دار در `localStorage` انجام می‌شود.
- داده‌ی ذخیره‌شده هنگام خواندن parse و validate می‌شود؛ داده‌ی خراب یا نسخه ناسازگار به حالت اولیه برمی‌گردد.
- هیچ داده‌ی حساس یا secret در storage قرار نمی‌گیرد.
- محتوای خاطرات و پرسش‌ها در فایل‌های TypeScript/JSON محلی و جدا از UI نگهداری می‌شود.

### مدل محتوایی پیشنهادی

```ts
interface MemoryItem {
  id: string;
  dateLabel?: string;
  title: string;
  caption: string;
  imageSrc: string;
  kind: "photo" | "milestone" | "fact";
}

interface QuizQuestion {
  id: string;
  prompt: string;
  acceptedAnswers: string[];
  hint?: string;
  successMessage?: string;
}
```

پرسش‌ها و پاسخ‌های صحیح صرفاً برای تجربه‌ی سرگرمی‌اند؛ چون برنامه‌ی استاتیک در مرورگر اجرا می‌شود، پاسخ‌ها قابل مشاهده در bundle هستند و نباید به‌عنوان داده‌ی محرمانه تلقی شوند.

## 7. معماری بصری و Design System

### Art direction

**Cute Pixel Art / 8-bit storybook**؛ نه رابط مدرن با چند آیکون پیکسلی تزئینی. تمام عناصر اصلی باید با منطق پیکسل‌آرت هماهنگ باشند.

### پالت اولیه

| Token | مقدار پیشنهادی | کاربرد |
|---|---|---|
| `--color-bg` | `#FFF8F2` | زمینه اصلی |
| `--color-surface` | `#FFFFFF` | پنل‌ها |
| `--color-pink` | `#F6AFC6` | رنگ تأکیدی |
| `--color-lilac` | `#C9B8F2` | رنگ مکمل |
| `--color-mint` | `#BFE8D2` | موفقیت/جزئیات |
| `--color-ink` | `#493B55` | متن و خطوط |
| `--color-yellow` | `#FFE39A` | ستاره و تاکید |

این مقادیر نقطه شروع‌اند و در بازبینی بصری فاز اول قابل تنظیم خواهند بود.

### قواعد بصری

- مرزها و سایه‌ها با پله‌های سخت و بدون blur طراحی شوند.
- گوشه‌های گرد بزرگ، گرادیان‌های نرم و glassmorphism استفاده نشوند؛ فرم‌ها باید pixelated باشند.
- از الگوهای تکرارشونده‌ی CSS برای پس‌زمینه و تزئینات استفاده شود.
- مقیاس پیکسل ثابت و منسجم باشد؛ از scaling غیرصحیح spriteها اجتناب شود.
- فونت متن فارسی خوانا و فونت تیتر/برچسب بازی پیکسلی باشد، مشروط به خوانایی حروف فارسی. فونت پیکسلی لاتین نباید برای متن فارسی تحمیل شود.
- دکمه‌ها حالت‌های default، hover، focus-visible، active و disabled واضح داشته باشند.
- انیمیشن‌ها کوتاه، هدفمند و قابل کاهش باشند.

### کاراکتر اختصاصی

- کاراکتر به‌صورت sprite asset محلی نگهداری می‌شود؛ نه تصویر خارجی hotlink شده.
- ساختار پیشنهادی: `public/assets/sprites/girlfriend/`
- حالت‌های احتمالی: idle، blink، wave، walk، celebrate.
- تا زمان دریافت تصویر مرجع و تأیید ظاهر، فقط placeholder موقت استفاده می‌شود.
- طراحی نهایی کاراکتر باید بر اساس تصویر مرجع ارائه‌شده و تأیید کاربر باشد.
- برای جلوگیری از تغییر شکل پیکسل‌ها از `image-rendering: pixelated` استفاده می‌شود.
- کاراکتر تزئینی با متن جایگزین مناسب یا `aria-hidden` علامت‌گذاری می‌شود؛ اگر حامل پیام باشد، متن معادل ارائه می‌شود.

## 9. قراردادهای فنی مهم

### Routing و GitHub Pages
- Router باید از `BASE_URL` تنظیم‌شده توسط Vite پشتیبانی کند.
- برای جلوگیری از 404 در refresh روی GitHub Pages، راهبرد hash routing یا fallback سازگار با میزبان در زمان scaffold انتخاب و مستند می‌شود. انتخاب پیش‌فرض پیشنهادی: `HashRouter` برای استقرار ساده در زیرمسیر repository.
- لینک‌های داخلی فقط از API مسیریابی استفاده می‌کنند.

### تصاویر و صدا
- تصاویر با ابعاد مناسب، فرمت WebP/PNG و بارگذاری lazy در صفحات غیرابتدایی.
- spriteها با PNG شفاف یا sprite sheet محلی.
- صدا فقط پس از اقدام صریح کاربر پخش شود؛ autoplay فرض نمی‌شود.
- کنترل play/pause، وضعیت بارگذاری و خطای پخش در UI وجود داشته باشد.
- فایل صوتی بدون نیاز به دسترسی شبکه‌ی ثالث از مسیر محلی ارائه شود.

### ورود تولد
- رمز تولد یک gate داستانی است، نه احراز هویت.
- هیچ ادعای امنیتی یا محرمانگی برای قفل سمت کلاینت مطرح نمی‌شود.
- ورودی با ارقام فارسی و لاتین normalize می‌شود؛ خطای ورودی واضح و قابل دسترس نمایش داده می‌شود.
- مقدار رمز واقعی تا زمان دریافت از کاربر در کد/مستندات ثبت نمی‌شود.

### دسترس‌پذیری
- ساختار معنایی HTML و ترتیب headingها.
- پشتیبانی کامل از keyboard و focus قابل مشاهده.
- کنتراست مناسب متن و کنترل‌ها.
- label و پیام خطای متصل به input.
- عدم اتکا به رنگ یا انیمیشن به‌تنهایی برای انتقال وضعیت.
- رعایت `prefers-reduced-motion`.

## 10. حریم خصوصی و امنیت

- اپلیکیشن بدون backend طراحی می‌شود؛ داده‌های شخصی در مرورگر و assetهای مخزن باقی می‌مانند.
- مخزن عمومی است؛ عکس، ویس یا اطلاعات شخصی فقط با آگاهی و اجازه‌ی صاحب محتوا در آن قرار گیرد. در صورت خصوصی‌بودن محتوا، پیش از انتشار عمومی باید visibility مخزن و روش میزبانی بازبینی شود.
- فایل‌های شخصی، اطلاعات EXIF، نام کامل، نشانی و metadata غیرضروری پیش از commit بررسی و در صورت لزوم حذف شوند.
- هیچ API key، token، رمز واقعی، فایل `.env` یا credential در مخزن قرار نگیرد.
- داده‌ی `localStorage` قابل دستکاری است و مبنای اعتماد امنیتی نیست.
- وابستگی‌ها حداقلی و lockfile commit می‌شود.
- لینک‌ها و محتوای خارجی در نسخه اول تا حد امکان حذف می‌شوند.

## 11. راهبرد تست و کیفیت

### Unit / Component
- normalize کردن ارقام فارسی و لاتین در ورودی.
- اعتبارسنجی رمز و پاسخ‌های quiz.
- محاسبه‌ی مرحله‌ی مجاز و انتقال state.
- parse و validate کردن persistence.
- تست کنترل‌های تعاملی، پیام خطا و کنترل صوت.

### Integration / E2E
- مسیر موفق از ورود تا پایان.
- ورود اشتباه و نمایش خطای قابل فهم.
- جلوگیری از ورود مستقیم به صفحات قفل‌شده.
- حفظ پیشرفت پس از refresh.
- بازگشت به صفحه قبل و حفظ پاسخ‌ها.
- replay و reset کامل.
- پخش/توقف ویس پس از تعامل کاربر.

### کیفیت رابط
- viewport موبایل و دسکتاپ.
- RTL و متن‌های فارسی طولانی.
- keyboard-only navigation.
- reduced motion.
- بررسی نبود overflow افقی و حفظ crisp بودن spriteها.

## 12. نقشه اجرای فازبندی‌شده

| فاز | خروجی | معیار پایان |
|---|---|---|
| 0 — معماری | این سند و تصمیم‌های پایه | ثبت در `docs/` و تأیید معماری |
| 1 — ورود | طراحی و پیاده‌سازی فقط EntryPage | حالت‌های idle/error/success، RTL، responsive و تأیید کاربر |
| 2 — خاطرات | MemoriesPage | timeline، رسانه‌ها و محتوای واقعی/تأییدشده |
| 3 — دعوت | InvitationPage | CTA و انتقال صحیح به بازی |
| 4 — بازی | QuizPage | validation، progress و حفظ پاسخ‌ها |
| 5 — پایان | FinalePage | تبریک، هدیه، audio controls و replay |
| 6 — یکپارچه‌سازی | تست جریان کامل، polish و انتشار | build و تست‌ها موفق؛ تأیید نهایی |

هر فاز شامل این چرخه است: مشخص‌کردن محتوای همان صفحه → طراحی بصری → پیاده‌سازی → اجرای تست‌های مرتبط → بازبینی → دریافت تأیید کاربر. خارج از صفحه جاری، فقط تغییرات زیرساختی ضروری و از پیش توافق‌شده مجاز است.

## 13. تصمیم‌های باز و ورودی‌های موردنیاز

این موارد مانع ثبت معماری نیستند؛ پیش از پیاده‌سازی صفحه مربوطه دریافت می‌شوند:

- سال یا رمز تولد مورد استفاده در صفحه ورود
- عکس‌های خاطرات و ترتیب/شرح آن‌ها
- تاریخ‌ها و رویدادهای شخصی مورد نظر
- آهنگ یا فایل صوتی مجاز برای استفاده
- متن و پاسخ پرسش‌های بازی
- پیام پایانی و فایل ویس
- تصویر مرجع کاراکتر و تأیید طراحی Sprite
- عمومی یا خصوصی بودن نهایی مخزن با توجه به حساسیت عکس‌ها و ویس

## 15. خلاصه تصمیم‌های معماری (ADR)

1. **SPA استاتیک به‌جای backend:** نیازمندی فعلی محلی و روایی است؛ backend پیچیدگی و سطح نگهداری غیرضروری اضافه می‌کند.
2. **React + TypeScript + Vite:** تعادل مناسب سرعت توسعه، ساختار و قابلیت نگهداری.
3. **CSS سفارشی به‌جای Tailwind در نسخه اول:** کنترل بصری pixel art و کاهش وابستگی.
4. **State سبک React + localStorage نسخه‌دار:** حفظ پیشرفت بدون store خارجی.
5. **یک صفحه در هر فاز:** کاهش دامنه‌ی تغییر و ایجاد گیت بازبینی/تأیید واقعی.
6. **Sprite محلی و placeholder تا دریافت مرجع:** کنترل کیفیت و جلوگیری از استفاده از تصویر نامرتبط یا بدون تأیید.
